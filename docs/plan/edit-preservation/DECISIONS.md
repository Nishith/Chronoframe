## Tie-break rule for new gaps
Choose the option that, in order: (1) keeps every `AGENTS.md` safety invariant; (2) changes the fewest existing files and lines; (3) copies an existing pattern from the reference file the WP names; (4) fails closed (refuse, mark unresolved, keep files, never delete). Log it as `D-EPR-1NN` with WP ID, options, choice. Never use the tie-break to weaken a safety rule; log that in `BLOCKED.md` instead.

## Product decisions
- **D-EPR-05 Edited export is opt-in, default off (approved by owner 2026-11-27).** Off keeps today's behavior and today's storage footprint.
- **D-EPR-06 Variant link is a stem convention for v1 (approved by owner 2026-11-27).** An edited variant is `<stem>-edited.<ext>` beside `<stem>.<ext>` in the same folder. Receipt-recorded links are a follow-up if the convention produces false positives. A user file that happens to be named `x-edited.jpg` beside `x.jpg` is protected by the same rule, which fails closed (it is never auto-trashed).
- **D-EPR-07 Stills only first (approved by owner 2026-11-27).** Edited renders of Live Photos and videos are not exported in v1; the import summary says "N edited videos / Live Photos not included". Claims for them need fixtures first (review, line 194).
- **D-EPR-08 Sidecars are copied byte-for-byte, never parsed or rewritten (approved by owner 2026-11-27).** No XMP/AAE fidelity promise.
- **D-EPR-09 Ambiguous or orphan companions are unresolved, never guessed (approved by owner 2026-11-27).** A companion with zero or more than one eligible owner is listed and not copied. Over-keeping is safe; mis-pairing is not.
- **D-EPR-10 Companion extensions (approved by owner 2026-11-27).** `.xmp` and `.aae` only. `.aae` also matches the iOS `IMG_E<n>.AAE` → `IMG_<n>.*` form (C-02).
- **D-EPR-11 No cache or schema migration (approved by owner 2026-11-27).** Companions are ordinary copy jobs, so `.organize_cache.db` and receipt JSON keep their schema (C-03). If WP-03's spike shows a schema change is unavoidable, apply D-EPR-16.

- **D-EPR-101 Caption helper (WP-01, default).** Options: extend `PhotosPreparationText` or add a new helper. Chose a new `PhotosImportEditsCaption` enum (`ui/Sources/ChronoframeApp/Views/Photos/PhotosImportEditsCaption.swift`) holding both C-01 strings; the view passes `includeEditedVersions: false` until WP-07 wires the toggle. - **D-EPR-102 `.aae` paths use on-disk spelling (WP-02, default).** iPhone writes `.AAE`; building `stem + ".aae"` would return a lower-case path on case-insensitive APFS (receipt and revert would then use a spelling the file never had) and miss the file on case-sensitive volumes. Options: 1) keep constructed paths; 2) resolve every sidecar extension against directory entries case-insensitively; 3) resolve only `.aae` (new behavior) and leave `.xmp` byte-for-byte. Chose 3: fails closed, keeps the INV-14 `.xmp` path unchanged (surgical). The same latent spelling issue for `.XMP` is pre-existing and flagged for a follow-up, not fixed here.

### WP-03 spike answers (2026-11-27)
- **D-EPR-103 Discovery hook (WP-03 Q1).** Entries come from `MediaDiscovery.walk` (`MediaDiscovery.swift:119-130`, the `isSupportedMediaFile` branch) and `enumerateManifest` (`:352-358`). Callers: `DryRunPlanner.swift:140`/`:504` (source), `:912`/`:1030` (destination index), `WatchedSourceFreshness.swift:84`, `GuardianLibraryProbe.swift:64`, `DeduplicateScanner.swift:76`. Choice: private `walk`/`enumerateManifest` gain an optional `visitCompanionPath` (default nil); existing public functions pass nil, so every other caller is unchanged; a new public `MediaDiscovery.discoverMediaAndCompanions(at:isCancelled:onDirectoryIssue:) -> (media: [String], companions: [String])` is used only at `DryRunPlanner.swift:140` and `:504`. Destination discovery stays media-only.
- **D-EPR-104 Planning hook is `DryRunPlanner`, not `CopyPlanBuilder.build` (WP-03 Q2).** `CopyPlanBuilder.build` (`CopyPlanBuilder.swift:102`) has no production caller; `DryRunPlanner.plan` and `planAsync` each fix destinations (primary `:691-754`, duplicates `:756-798` in `planAsync`; same blocks in `plan`). Choice: one pure helper (new `CompanionResolver.swift`) called from both, right after the duplicate loop and **after** `dateHistogram` is computed from owner transfers only. Companion jobs: destination derived from the owner's `PlannedTransfer.destinationPath` (C-03.4), `dateBucket`/`isDuplicate` copied from the owner, identity from `FileIdentityHasher` (required: executor re-hashes against it and revert trusts it). Companions never enter `sourceSeen`, `pathsByIdentity`, review overrides, `counts.newCount`/`duplicateCount`/`hashErrorCount`, or the histogram. `DryRunPlanner.swift` joins WP-04's owned paths; `CopyPlanBuilder.build` is left unchanged except the `unresolvedCompanions` field on `CopyPlanResult`.
- **D-EPR-105 No executor, receipt, revert or cache schema change (WP-03 Q3).** `TransferExecutor` has no extension checks (copy `:882-1038`, receipt `appendTransfer` `:1502-1703`, schema v3 unchanged); `RevertExecutor` walks every transfer hash-gated (`:350-402`, `:425`); `CopyJobs` keyed by `src_path`, `FileCache` by `(id, path)`, no unique hash index (`OrganizerDatabase.swift:243-265`, schema 4). `CopyPlanResult` is not persisted in production (custom `init(from:)` `CopyPlanBuilder.swift:71-83`; add the field with `decodeIfPresent ?? []`). D-EPR-11 holds; D-EPR-16 not triggered. Residual executor-adjacent gaps are logged as B-2 (non-blocking).
- **D-EPR-106 Other surfaces (WP-03 Q4).** Watched Sources (`WatchedSourceFreshness.swift:74-105`, `SourceWatchCoordinator.swift:407-423`) and preview review rows (`PreviewReviewStore`, `PreviewReviewSummary`) see media only; no change. Counts that would include companions: `RunMetrics.plannedCount` (`SwiftOrganizerEngine.swift:537, 1003`), headline `RunPreviewHeadline.swift:36-40`, hero `RunWorkspaceModel.swift:316`. One leak found: `LibraryHealthScanner.cachedDuplicateStats` (`:320-341`) groups all destination `FileCache` rows by hash, so byte-identical `.aae` files would show as duplicates. Choice: filter those rows to `isSupportedMediaFile` (one line; `LibraryHealthScanner.swift` joins WP-04 paths).
- **D-EPR-107 Free test batch keeps owners and companions together (WP-04, default).** `FreeTestBatchPlanner.batch` takes a prefix by `(dateBucket, sourcePath)`, so a batch could hold a companion without its owner, which would land at a name its owner never takes. Choice: `DryRunPlanningResult` carries an in-memory `companionOwners: [String: String]` (companion source → owner source, not Codable), and `reduced(to:)` drops any companion whose owner is not kept. No purchase or authorizer code changes; the authorized count can only shrink. Companions count as files toward the trial allowance (no metering change).
- **D-EPR-108 Drag-and-drop manifests (WP-04, default).** In manifest mode only companions that were themselves dropped are candidates; siblings of a dropped photo are not probed (manifest mode never lists parent folders today).
- **D-EPR-109 Live Photo owners (WP-04, default).** C-03.3 counts every media file as an eligible owner, so `IMG_1234.AAE` beside a Live Photo `IMG_1234.HEIC` + `IMG_1234.MOV` has two owners and is unresolved. Kept as written (fails closed). Owner may flip to "photo owners first, video only when no photo matches".
- **D-EPR-110 Unresolved reasons (WP-04, default).** C-03.6 needs a reason per item, which `[String]` cannot carry. `CopyPlanResult.unresolvedCompanions` is `[UnresolvedCompanion]` (`sourcePath`, `reason`: `.multipleOwners`, `.noOwner`, `.nameTaken`, `.unreadable`). Copy: `Not copied: <name> (matches more than one photo)`, `(no matching photo)`, `(that name is already taken in the destination)` for C-03.5 and D-EPR-14, `(could not be read)` for a companion whose hash fails.
- **D-EPR-111 Execution-time name race (WP-04, default, residual).** The planner checks `fileExists` and planned-name clashes; `TransferExecutor.collisionResolvedPath` (`:1074-1099`) can still rename a job `_collision_N` if a file appears in the destination between plan and copy (only an outside writer, since INV-19 locks out Chronoframe). A companion could then end up apart from its owner. No overwrite happens (INV-04 holds). Accepted and documented in SAFETY_AND_RECOVERY.md; fixing it needs an executor change (B-2).
- **D-EPR-112 `reduced(to:)` lives in `FreeTestBatchPlanner.swift` (WP-04, default).** D-EPR-107's change belongs to `DryRunPlanningResult.reduced(to:)`, declared at `FreeTestBatchPlanner.swift:164`, not in `DryRunPlanner.swift`. That file is plan-reduction logic, not StoreKit or purchase code. Options: 1) orchestrator patches it; 2) add that one function to WP-04's owned paths. Chose 2: the implementer edits only `reduced(to:)`; `batch`, `FreeTestBatchSelection.apply`, `TrialAuthorizer` and metering are untouched.
- **D-EPR-113 Companion counts in `RunMetrics` (WP-04 part 2, default).** C-03.9's split needs counts the engine already has. `RunMetrics` gains `plannedCompanionCount`, `copiedCompanionCount`, `unresolvedCompanionCount` (decoded with `decodeIfPresent ?? 0`, so stored history still reads). Not a cache or receipt change (D-EPR-11 holds).
- **D-EPR-114 Unresolved companions surface as warning issues (WP-04 part 2, default).** Options: new preview model and view, or one `RunIssue(.warning)` per unresolved companion after planning. Chose issues: the existing preview surface, no new UI, Core templates localized through `CoreL10n`.
- **D-EPR-115 Copied companion count from the run's receipt (WP-04 part 2, default).** `copiedCompanionCount` counts companion destinations in the finalized `audit_receipt_*<runID>*.json` via the existing read-only `RevertExecutor().loadReceipt`; if no receipt matches, it uses the planned count only when nothing failed or was skipped and every planned transfer copied, otherwise 0 (no split shown). Unresolved warnings are emitted in preview and transfer (shared post-planning path); they are warnings, so they never mark a run as having problems. German term for "sidecar file": "Begleitdatei".
- **D-EPR-116 How the edited file flows (WP-06, default).** The edited file is staged like any other file of its asset: it is in `PhotosCompletedAssetRecord.files` (so resume validation, reserved names and the Organize hand-off cover it unchanged) **and** named in `editedFile`. Its `SourceDateHint` uses the asset's capture date resolved from the originals only. The executor takes `includeEditedVersions: Bool = false`; new events `.editedVersionSaved(assetID:file:)` (just before that asset's `.assetCompleted`), `.editedVersionFailed(assetID:)` and `.editedVersionNotIncluded(assetID:)`; `PhotosExportReceipt` gains `editedFiles`, `variantFailures`, `editedNotIncludedCount` (defaulted). A failed render rolls back only the edited file; cancellation rolls back the whole asset including it.
- **D-EPR-117 Detecting edits that are not exported (WP-06, default).** `editedStillResource` returns the `.fullSizePhoto` only for a still without a paired video (D-EPR-07: no Live Photo or video edits). To count "edited videos and Live Photos not included", `PhotosResourceExporting` gains one more read-only method with a nil-safe default, `hasUnsupportedEditedRender(forAssetID:) async throws -> Bool` (`.fullSizeVideo`, or `.fullSizePhoto`/`.fullSizePairedVideo` on an asset with `.pairedVideo`), implemented with `PHAssetResource.assetResources(for:)` only. Options considered: throwing a sentinel error from `editedStillResource` (misuses errors), or skipping the count (C-04 requires it).
- **D-EPR-118 Store wiring split (WP-06/WP-07, default).** Resume lives in `PhotosImportStore`, so WP-06 owns the minimal store wiring: record `editedFile` and variant failures into the checkpoint, store `includeEditedVersions` in a new checkpoint, and pass the checkpoint's value on Resume. WP-07 owns the toggle, the choice passed at start, and all summary text.
- **D-EPR-119 Not-included count survives Resume; stale variant failures cleared (WP-07, default).** WP-06 review found that `.editedVersionNotIncluded` is in-memory only, and a variant failure recorded for an asset that resume validation re-exports stays after a successful retry. Choice: WP-07 adds `editedNotIncludedAssetIDs: [String]` to the checkpoint (`decodeIfPresent ?? []`, no version change; still v2), records it from the event, and `discardCompleted` also drops that asset's variant failure and not-included entry. `PhotosImportCheckpoint.swift` joins WP-07's owned paths for these two changes only.
- **D-EPR-120 Import counts also show in the Organize run (WP-07, default).** After prepare, the app moves to Organize › Run, where the real pre-transfer review and summary live; a Photos-view footer alone would go unseen. The edited-photo preview line and the `Originals · Edited versions · Could not save` summary show in the Run view for a run whose source is the active Photos import, and stay in the Photos footer. WP-07's owned paths extend to `Views/Run/*`, `RunCoordinator.swift` and `AppState.swift` for read-only display wiring. The toggle lives on `PhotosImportStore.includeEditedVersions` (never persisted); `prepareImport(includeEditedVersions: Bool? = nil)` uses it when nil.
