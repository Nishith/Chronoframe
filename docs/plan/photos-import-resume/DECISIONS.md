# Photos import resume — decisions

Plan prefix `PIR`. Resolves every gap the Round 3 review and the contracts leave open. Runtime decisions go at the bottom as `D-PIR-1NN`.

## Tie-break rule for new gaps
When a gap appears that no contract or decision covers, choose the option that, in this order: (1) keeps every `AGENTS.md` safety invariant, INV-22 above all; (2) changes the fewest existing files and lines; (3) copies an existing pattern from the reference file the WP names; (4) fails closed (refuse, mark unresolved, keep files and checkpoint, never delete). Log it as `D-PIR-1NN` with the WP ID, the options and the choice. Never use the tie-break to weaken a safety rule; log that in `BLOCKED.md` instead.

## Scope and process
- **D-PIR-01 Branch (revised 2026-11-12, owner).** `feature/photos-import-resume`, stacked on `feature/dedupe-persistence` @ 97fc546 (itself stacked on `feature/nas-v1`), because neither is merged to `main` yet. Guards that take a base ref use `feature/dedupe-persistence`. Never push; the owner opens the pull request. If the branch does not contain `docs/plan/photos-import-resume/`, WP-00 stops with a BLOCKED entry.
- **D-PIR-02 Plan location.** `docs/plan/photos-import-resume/`. Shared rules: `docs/plan/next-half/AGENT_RULES.md`.
- **D-PIR-03 Test placement.** AppCore tests in `ui/Tests/ChronoframeAppCoreTests/` named `Photos<Thing>Tests.swift` (matches `PhotosImportStoreTests.swift`); App tests in `ui/Tests/ChronoframeAppTests/` named `Photos<Thing>Tests.swift`. No XCUITests; `project.pbxproj` is never edited.
- **D-PIR-04 No bounded batches this plan.** Exporting the selection in batches and transferring each batch would require a reviewed plan per batch or a plan over not-yet-exported files. That changes the review contract. This plan keeps one staging set per import and makes it resumable and space-aware. Bounded batching stays NAS P1.
- **D-PIR-05 Capacity is a floor, not an estimate.** `PhotosAssetSummary` carries no byte size and PhotoKit has no public pre-export size. The executor checks free space before each asset and stops cleanly below 2 GiB (`defaultFreeSpaceFloorBytes`). No upfront estimate is shown as a number; the first-ten-minutes plan shows the staging volume's free space as a fact.
- **D-PIR-06 Checkpoint lives in the staging directory.** `<staging>/.chronoframe_photos_checkpoint.json`. The staging directory is the Organize source for the run; the file is hidden and `.json` is not a supported media extension, so discovery ignores it. `cleanupStaging(for:)` after a run removes it with the directory.
- **D-PIR-07 Resume validates existence and size, not content.** Rehashing gigabytes to offer a Resume card is wasteful; `DryRunPlanner.resolveSourceDate` already rehashes every hinted file at preview and aborts on an identity mismatch (`SourceDateHintError.changed`). Resume therefore checks each completed file exists with its recorded `identity.size`; the planner remains the content gate.
- **D-PIR-08 One resumable import at a time.** `refreshResumableImport` keeps the newest valid checkpoint and removes older staging directories. Starting a new import while one is resumable requires the confirmation dialog in C-05.
- **D-PIR-09 Strings.** New UI strings are Swift literals; the orchestrator adds English keys to `ui/Sources/ChronoframeApp/Resources/Localizable.xcstrings` and `ui/Sources/ChronoframeAppCore/Resources/LocalizableCore.xcstrings` at G2 with `docs/plan/next-half/bin/add_xcstrings_keys.py`. Translations are an owner step.
- **D-PIR-10 Failures are terminal per asset.** A failed asset is recorded in the checkpoint and skipped on resume; the user retries by selecting it again in a new import. No automatic retry.
- **D-PIR-11 Executor event payload.** `.assetCompleted` carries the asset's files and hints (C-04 amendment to C-02) so the store can checkpoint per asset without waiting for the receipt. The receipt type is unchanged.
- **D-PIR-12 Progress thresholds.** `isWaitingForCloud` turns on at the first `resourceProgress` with fraction < 1 for the current asset and off at that asset's completion or failure. No timers.
- **D-PIR-13 `isPreparingImport` stays.** It becomes computed from `preparation != nil` so `PhotosImportView` and existing tests keep compiling.
- **D-PIR-14 Staging override is DEBUG-only.** `CHRONOFRAME_PHOTOS_STAGING_DIR` lets the owner point staging at a small disk image to exercise the low-space path. Release ignores it.
- **D-PIR-15 AGENTS.md line 131 changes.** The sentence "Staging is deleted on completion, failure, or cancellation" is no longer true and is replaced by the C-08 text at G2 by the orchestrator. INV-22 is untouched; new executor and store tests are tagged `// AGENTS-INVARIANT: 22`.

## Runtime decisions
(appended by the orchestrator as D-PIR-1NN)
- **D-PIR-101 (WP-01) `MediaKind` gains `Codable`.** C-01 assumed `PhotosAssetSummary.MediaKind` (`ChronoframeCore/PhotosCatalog.swift:13`) was already encodable; it is `String`-raw but did not declare `Codable`, so `PhotosAssetExportEntry` could not synthesize it. Options: (A) add `Codable` to that one conformance list; (B) hand-written `init(from:)`/`encode(to:)` on the entry. Chose A by the tie-break (fewest lines, no new code); WP-01's owned paths are extended by that one line.
- **D-PIR-102 (WP-02) No-original-resource branch emits `.assetFailed`.** C-02 rule 3 names only the catch branch, but the "no original resource" branch also records a failure after `.assetStarted`. Without an event the store could not checkpoint that failure and a resume would retry the asset forever. Chose to emit `.assetFailed` with the same message (tie-break 4, fail closed); the message is hoisted to a local, string unchanged.
- **D-PIR-103 (WP-02) Free-space check precedes `.assetStarted`.** A low-space stop therefore leaves no started-but-unfinished asset in the event stream.
- **D-PIR-104 (WP-02) Pre-existing filename collision classes left untouched; flagged for the owner.** (a) `uniqueFilename` does not re-check the folded `stem-<resourceIndex>.ext` name against `used`: plan [P stem `IMG_0001-2`, Q stem `IMG_0001` with two same-extension resources at indexes 0 and 2] folds Q's second file onto P's published `IMG_0001-2.jpg`; a failed write would then roll back P's file. (b) Stems and used names are case-sensitive while staging is usually case-insensitive APFS. Both exist on the base branch within a single export; resume adds no new path to them (plan order is preserved and reserved names are the same set). Not fixed here: safety-critical file, change discipline. Recommended follow-up: loop the folded name against `used` and compare case-insensitively, with its own INV-22 test.
- **D-PIR-105 (WP-04) Resume removes files the checkpoint does not record.** A hard crash mid-asset can leave an unrecorded file under a final name (a Live Photo still without its movie) or a `.photoexport.tmp`. If that asset then fails early on resume nothing rolls it back and it would reach the transfer pipeline as a partial unit. `resumeImport` removes every staging child that is neither the checkpoint file nor a recorded completed filename before exporting, and fails closed (no export, directory and checkpoint kept, existing "couldn't prepare" text) if one cannot be removed. Tests tagged INV-22.
- **D-PIR-106 (WP-04) Resume revalidates at resume time.** `resumeImport` re-runs `refreshResumableImport(destination:)` with its own argument before the remaining guards, so a destination changed or a recorded file removed after the last refresh refuses the resume (A-PIR-04).
- **D-PIR-107 (WP-04) Two existing tests filter the checkpoint file out of their staged-file count.** D-PIR-06 puts the checkpoint in the staging directory; the expectation is still two media files.
- **D-PIR-108 (WP-04) The staging parent is removed only when it ends up empty** after an empty-result or failed prepare (an existing test asserts the parent is gone). A parent holding anything is never touched.
- **D-PIR-109 (WP-04) Prepared staging is protected from refresh.** The store keeps a private set of staging paths handed out in a context; refresh skips them until `cleanupStaging(for:)` or the next prepare. Without it, refresh on view appear would delete the `.ready` directory of an import still in preview or run. The set is in memory: after a relaunch a `.ready` directory is removed by the launch refresh, as C-04 specifies; see the final report for the consequence for an interrupted transfer.
- **D-PIR-110 (WP-04) Refresh and discard are no-ops while a prepare runs;** refresh skips non-directories and symlinks; a completed file with no recorded hint, or not a regular file, counts as damaged. Newest-wins ties break by `createdAt`, then `importID`.
- **D-PIR-111 (WP-04) `testPurgeStagingParentNoLongerExists` follows C-04, not the WP wording:** a new prepare over two valid checkpoints removes both (older by refresh, newest by supersede); the test also asserts a stray file in the parent survives.
- **D-PIR-112 (WP-04) `resumeImport` returns nil without a message** when there is no resumable import or a prepare is running (C-06 has no string for either).
- **D-PIR-113 (WP-04) Checkpoint saves use `try?`.** A failed save never aborts the export; the cost is a smaller resume offer than the stop message stated, never a lost original. Flagged for the owner as a possible follow-up (treat a failed save as a low-space stop).
- **D-PIR-114 (WP-04) Event ordering and label.** Executor events go through one `AsyncStream`, are applied on the main actor in order and drained before the outcome is judged. `currentAssetLabel` comes from `selectedSummaries` and is nil for a resume after relaunch. `PhotosPreparationProgress` and `PhotosResumableImport` have internal memberwise initializers (no extra public API).
- **D-PIR-115 (WP-05) String rendering follows the dedupe-persistence pattern.** Fixed constants (`waitingForCloud`, `destinationMismatch`) render as `Text(LocalizedStringKey(…), bundle: .module)` so catalog translations apply; computed count/date strings render with `Text(verbatim:)` and are English-only until a format-key pass, as in `DeduplicateReviewCopy`. The panel's `ProgressView` takes the progress line as its accessibility label.
- **D-PIR-116 (WP-05) View test hooks and formatting parameters.** The two views expose internal properties the body itself uses (`stopButtonIdentifier`, `showsCloudWait`, `resumeButtonIdentifier`, `discardButtonIdentifier`, `isResumeDisabled`, `showsDestinationMismatch`); `PhotosPreparationText` functions take defaulted `locale`/`timeZone`; internal `supersedeMessage(readyCount:locale:)`; the progress bar value is clamped to its total; the panel sits in the footer capped at 360 pt.
- **D-PIR-117 (WP-06) Test harness never touches the real staging folder.** `AppStateHarness.makeAppState` bootstraps by default, so the C-07 launch refresh would have scanned and pruned the user's real `Application Support/Chronoframe/photos_import_staging` during test runs. The harness now always injects a `PhotosImportStore` staged in its own temp directory (removed in `deinit`); WP-06's owned paths are extended by `TestSupport.swift`. No test detection in production code.
- **D-PIR-118 (WP-06) Seam and assertion substitutions.** `AppState.photosStagingParentURL(environment:)` is an internal static seam for the DEBUG override test. `runCoordinator` is private, so `testResumeInterruptedPhotosImportStartsPreviewWithRestoredContext` asserts `hasActivePhotosImport` and the preview configuration the mock engine received (mode, staging source, destination, hint keys) instead of `activePhotosImportContext?.assetIDs`. The launch refresh runs only when `performInitialBootstrap` is true, after bookmark restore and mutation recovery.
- **D-PIR-119 (WP-06) Empty `CHRONOFRAME_PHOTOS_STAGING_DIR` is ignored.** An empty value would resolve to the current working directory and the refresh would prune it; the DEBUG override now requires a non-empty value.
- **D-PIR-120 (G2) AGENTS.md staging sentence and string catalogs.** The C-08 replacement text said partial assets are "always rolled back"; a hard crash cannot roll back, so the applied sentence says a partial asset is rolled back or, if the app died mid-write, removed before the resume exports anything (D-PIR-105), and keeps the existing "Photos library is never modified" clause. String keys were added with an inline script that preserves each catalog's existing JSON style (the shared `add_xcstrings_keys.py` still re-serializes, D-DDP-117): 8 keys in `Localizable.xcstrings` (`strings-app.txt`), 2 in `LocalizableCore.xcstrings` (`strings-core.txt`); "Stop" already existed. Count- and date-bearing strings are rendered verbatim and have no catalog keys (D-PIR-115).
- **D-PIR-121 (PR #268 review, item 1) Prepared-staging protection is never reset by a new prepare.** `prepareImport` no longer clears `preparedStagingPaths`; a path leaves the set only through `cleanupStaging(for:)`. Amends D-PIR-109 ("or the next prepare"). A run still reading an earlier prepared import can no longer lose its directory to the refresh a new prepare triggers.
- **D-PIR-122 (item 2) Refresh deletes only what Chronoframe created.** A staging-parent child is examined only if it is named by an import UUID (how `prepareImport` names it) or holds the checkpoint file; anything else is skipped, never deleted. `refreshResumableImport` never removes the parent. `removeEmptyImportDirectory` (D-PIR-108) is unchanged and still removes an emptied parent after an empty or failed prepare; flagged: with the DEBUG override pointing at an empty pre-existing folder that folder would go, which this change did not touch.
- **D-PIR-123 (item 3) A failed checkpoint save stops the export; supersedes D-PIR-113.** The per-asset save is checked: on failure the in-memory checkpoint is not advanced, the executor is cancelled, and the run ends like the low-space pause (`.lowSpace`, resume card, plain message "couldn't save its progress ... may be full"). The disk checkpoint stays the source of truth, so a file written but never recorded is removed by the resume (D-PIR-105). Chosen: the pause and final `.ready` saves stay best-effort (`try?`): a pause that cannot save leaves the earlier checkpoint, and a failed `.ready` save leaves every asset already recorded (only the state differs; a crash then offers a resume that exports nothing). A failed *first* save of a new import (nothing exported yet) keeps the existing "couldn't prepare" message and removes the empty directory.
- **D-PIR-124 (item 8) Superseded import deleted after the new import's first checkpoint saves.** `prepareImport` remembers the superseded directory and `runExport` deletes it right after the new import's initial checkpoint is saved. Options: (A) after the first checkpoint save, (B) after the first completed asset, (C) only on success. Chose A (the wording of the review item, tie-break 4 for the failure that matters: a full or unwritable staging volume); B/C would leave two resumable imports around when a stop happens early and D-PIR-08 (one at a time) would pick the newer, empty one.
- **D-PIR-125 (item 4) Hintless asset is re-exported; paths must resolve inside staging.** Amends D-PIR-110. An asset with a completed file lacking a recorded source-date hint is dropped from the checkpoint at validation (`discardCompleted`), so it is exported again and its files are removed as unrecorded (D-PIR-105); the other assets are kept. Any recorded path that does not, after standardizing and resolving symlinks, lie under the import's own resolved staging directory invalidates the whole checkpoint (its directory is removed, nothing outside it is touched). A missing file, a non-regular file or a size mismatch still invalidates the whole checkpoint (D-PIR-07).
- **D-PIR-126 (item 5) Failed assets are retried on resume; supersedes D-PIR-10.** `resumeImport` clears the checkpoint's failures before exporting, so they are exported again with the unfinished assets. An asset that fails again is recorded again. A `.ready` checkpoint is still never resumable, so a finished import's failures are not retried automatically.
- **D-PIR-127 (item 7) Resume validates the card's own directory.** Amends D-PIR-106 and D-PIR-112. `resumeImport` takes the `resumable` the card shows, re-validates only that directory (destination and files as they are now) and resumes it; it no longer runs the full refresh first, which could pick or delete another import. If that directory is gone or invalid it runs the refresh (so the card shows what really exists), sets "That interrupted import is no longer available. Your Photos library was not changed." and resumes nothing. With no `resumable` at all it still returns nil silently. The "couldn't prepare" text for this case in `testResumeRevalidatesDestinationAndFilesAtResumeTime` was updated to the new message.
- **D-PIR-128 (item 6) Asset size joins the low-space threshold.** Amends D-PIR-05 and D-PIR-103. `PhotosExportableResource` gains `fileSize: Int64?` (default nil). After an asset's resources are listed the executor stops with `PhotosExportStop.lowStagingSpace` when free space is below floor + the asset's summed known sizes (`floorBytes` in the stop is that threshold). The first, size-less check before `.assetStarted` is unchanged, so D-PIR-103 holds for it; the size check runs after `.assetStarted`, and nothing of the asset is written. Unknown sizes and unknown free space never stop the export. `PhotosResourceExportService` reads the size with `value(forKey: "fileSize")` on `PHAssetResource`, guarded by `responds(to:)`. **Owner decision:** PhotoKit has no public size property; `fileSize` is an undocumented KVC key that many apps use. If App Review is a concern, delete `fileSize(of:)` and pass nil: the executor then behaves exactly as before for production while the tested threshold logic stays in place.
